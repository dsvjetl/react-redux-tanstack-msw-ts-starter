# Research: Daily Todo Planner

**Feature**: `001-daily-todo-planner` | **Date**: 2026-09-22

All unknowns from the plan's Technical Context are resolved below. Versions were checked
against the npm registry on 2026-09-22.

## R1. Native packaging: Capacitor 8 for Android

**Decision**: Add Capacitor 8 (`@capacitor/core`, `@capacitor/cli`, `@capacitor/android` 8.5.x)
with `webDir: 'dist'`, `server.androidScheme: 'https'`, and the official plugins
`@capacitor/app` (hardware back button, app state), `@capacitor/preferences` (storage, see R2),
`@capacitor/status-bar`, `@capacitor/splash-screen`, `@capacitor/keyboard` and
`@capacitor/haptics`. The `android/` project generated by `npx cap add android` is committed.

**Rationale**: Capacitor is the standard way to ship a Vite/React SPA as an Android app while
keeping one codebase. Version 8 is current and requires Node 22+ (the repo's `.nvmrc` pins
23.4.0, which satisfies it), JDK 21 and Android Studio Otter 2025.2.1+. The WebView loads
`index.html` from the bundled `dist/` and serves it at `https://localhost`, so no server is
needed. Capacitor is bundler-agnostic, so the existing Vite 6 build is kept unchanged.

**Alternatives considered**: React Native / Expo (rewrite of every component, incompatible
with the starter and the SCSS Modules rule); Tauri Mobile (younger Android story, Rust
toolchain); PWA/TWA only (no native plugins, weaker install and storage guarantees).

**Environment note**: the current machine has no JDK and no `ANDROID_HOME`, so Android builds
need Android Studio installed first (see quickstart). Web development and tests do not.

## R2. Persistence: Capacitor Preferences with a versioned JSON document

**Decision**: Persist a single versioned document (`{ version: 1, tasks, occurrenceStates,
overrides }`) as JSON under one key in `@capacitor/preferences`, behind a `TaskRepository`
interface with two implementations: `PreferencesTaskRepository` (production) and
`InMemoryTaskRepository` (tests and `npm run dev:mock`, seeded with sample data).

**Rationale**: Preferences maps to Android `SharedPreferences`, which is not subject to WebView
storage eviction, and to `localStorage` on the web, so the same code runs in the browser during
development. The spec's scale target (200 tasks across 4 weeks) is well under 100 KB, so
rewriting the whole document on each mutation is cheap and keeps the code trivial. The
repository interface keeps a later move to SQLite a local change.

**Alternatives considered**: Dexie/IndexedDB (rich queries, but Android WebView may evict
IndexedDB under storage pressure, which violates SC-005's 100% retention target);
`@capacitor-community/sqlite` (real database, but needs `jeep-sqlite` and a WASM bundle for
web, has had rough major-version migrations, and is overkill for this data size); Capawesome
SQLite (commercial insiders plugin). SQLite is the documented escalation path if data grows.

## R3. State ownership: TanStack Query over the repository, Redux for UI state

**Decision**: The persisted document is loaded through one query (`['planner']`) and changed
through mutations that apply a pure command function (`applyCommand(doc, command) → doc`) and
then `repository.save`. Mutations update the query cache optimistically and roll back on error.
Redux Toolkit holds only shared client state: `calendarSlice` (selected week start) and
`taskEditorSlice` (editor sheet open/closed, mode, target task/occurrence, prefilled date).

**Rationale**: The constitution assigns persisted/async data to TanStack Query and shared
client state to Redux. Storage access is async and has loading/error states, exactly what
Query models. Keeping all domain changes as pure functions makes recurrence and series-split
logic unit-testable without React or storage. Redux stays tiny.

**Alternatives considered**: Redux slice holding the tasks with a persistence middleware
(duplicates the async-state machinery Query already provides and breaks Principle III);
Zustand (a third state library the constitution does not allow).

## R4. Dates and times: `date-fns` 4 with ISO string fields

**Decision**: Store dates as `YYYY-MM-DD` strings and times as `HH:mm` strings; interpret both
in the device's local time zone. Use `date-fns` 4.4.x for parsing, formatting, week ranges,
day arithmetic and weekday checks. Never store `Date` objects or UTC timestamps for task dates.

**Rationale**: Calendar dates for daily habits must not shift when the device time zone
changes; local-date strings are the standard way to avoid that. `date-fns` is tree-shakable,
immutable, typed, and has first-class formatting for the reference's labels ("Monday, Apr 15",
"10 – 15 Apr").

**Alternatives considered**: Day.js (smaller but mutable-feeling plugin API); Luxon (heavier,
Intl-based); Temporal (not yet universally shipped in Android WebView without a polyfill).

## R5. Recurrence: small custom expansion, not `rrule`

**Decision**: Implement `occurrencesInRange(task, from, to)` as a pure function that expands
the three supported rules (every day, weekdays, weekly on chosen days) with an optional
inclusive `endDate`, applies per-occurrence overrides, and attaches per-occurrence state.

**Rationale**: The spec limits rules to three simple shapes with no intervals, counts or
exceptions beyond "this occurrence only". That is roughly 60 lines of well-tested code. `rrule`
(2.8.x) is ~50 KB, carries known time-zone pitfalls, and would make the stored rule an opaque
string that the form must parse back.

**Alternatives considered**: `rrule` (rejected as above; revisit if monthly/yearly rules are
requested); storing pre-generated occurrences (unbounded growth, and series edits become
mass updates).

## R6. Accessible UI primitives: Radix Primitives via the unified `radix-ui` package

**Decision**: Use `radix-ui` 1.6.x (one dependency exporting all primitives) for Dialog
(task editor bottom sheet and task detail), AlertDialog (delete and series-scope prompts),
Checkbox (task and sub-item done), RadioGroup / ToggleGroup (repeat rule and weekday picker),
Label and VisuallyHidden. All styling is SCSS Modules on Radix's `data-state` attributes.

**Rationale**: Radix is headless, so it satisfies the constitution's SCSS-Modules-only and
no-inline-style rules while providing focus trapping, keyboard handling and ARIA wiring that
FR-016 and SC-007 require. The unified package avoids a dozen `@radix-ui/react-*` entries.

**Alternatives considered**: shadcn/ui (Tailwind-based; conflicts with SCSS Modules rule);
React Aria Components (excellent, but heavier bundle and less familiar to the team);
`vaul` for the bottom sheet (last published 2 years ago and no longer maintained, so the
sheet is a Radix Dialog positioned at the bottom and animated with Motion, see R8).

## R7. Forms and validation: React Hook Form 7 + Zod 4

**Decision**: `react-hook-form` 7.88.x with `@hookform/resolvers` 5.9.x and `zod` 4.6.x. One
`taskFormSchema` in `src/shared/models/Task.ts` is the single source of the FR-004 rules
(title 1–120, sub-items ≤ 10 × 1–80 chars, time in 5-minute steps, weekly rule needs ≥ 1
day) and also validates documents loaded from storage.

**Rationale**: RHF gives uncontrolled, fast inputs on low-end Android WebViews; Zod 4 gives
one schema for both form validation and storage parsing, so the "storage corrupted" edge case
is a schema failure handled in one place.

**Alternatives considered**: Formik (slower re-renders, less active); TanStack Form (good, but
RHF's Radix integration examples are more mature); Yup (weaker TypeScript inference).

## R8. Animation: CSS keyframes on Radix `data-state` (revised during implementation)

**Decision**: Use CSS keyframes for the bottom-sheet slide and the "Up next" card rise, driven
by Radix's `data-state="open|closed"` attributes and the `--motion-*` tokens, which collapse to
`0ms` under `prefers-reduced-motion`. The `motion` package was evaluated, briefly wired for the
"Up next" card, and removed before completion.

**Rationale**: The feature has three small animations, all of which Radix + CSS cover
(Radix keeps the dialog mounted until the close animation ends). Shipping a ~35 KB gzipped
animation runtime for one fade was not justified by the constitution's YAGNI rule, and CSS
animations behave identically in headless/WebView contexts where JS-driven animations were
observed to stall.

**Alternatives considered**: `motion` 13 (original choice; rejected as above, revisit if
gesture-driven or layout animations are added); `react-spring` (same trade-off).

## R9. Icons: `lucide-react`

**Decision**: `lucide-react` 1.x for the plus, check, repeat, chevron, list and calendar icons.
Every icon-only button gets an `aria-label`.

**Alternatives considered**: `@radix-ui/react-icons` (smaller set, no repeat icon); inline SVG
files (fine, but lucide's consistency matches the reference's rounded style).

## R10. Week calendar view: custom CSS Grid, no calendar library

**Decision**: Build the Calendar as a CSS Grid with one column per day and hour rows 6 AM to
11 PM, an "Anytime" row above the grid, and occurrence blocks positioned by
`grid-row` computed from the time. Horizontal scrolling on narrow screens shows 3 days at a
time with today first.

**Rationale**: Calendar libraries (react-big-calendar, FullCalendar, Schedule-X) ship their own
CSS, event models and time-slot behaviours that fight the reference design and the SCSS
Modules rule; the spec needs a read-mostly week grid without drag-and-drop or resizing.

**Alternatives considered**: react-big-calendar (Moment/date-fns localizer, hard to restyle);
FullCalendar (large, premium features licensed); Schedule-X (modern but opinionated theming).

## R11. Routing on Android: React Router 7 `BrowserRouter` with hardware back button

**Decision**: Keep `BrowserRouter`. Routes are `/` (Today) and `/calendar`; both contain no
dots, so Capacitor's local server serves `index.html` for them. Register a
`@capacitor/app` `backButton` listener in an `AppShell` effect: if the editor sheet or a dialog
is open, close it; else if history can go back, `navigate(-1)`; else `App.exitApp()`.

**Rationale**: The constitution mandates `BrowserRouter`. The known Capacitor pitfall only
affects paths containing a dot, which this app never uses. Android users expect the back
button to close sheets before leaving the app.

**Alternatives considered**: `HashRouter` (works everywhere but produces uglier URLs and is
unnecessary here); `MemoryRouter` (breaks web deep links during development).

## R12. Testing strategy

**Decision**: Keep Vitest 2 + Testing Library (already installed) and add
`@testing-library/user-event` 14.x. Component tests render with a `renderWithProviders` helper
(Query client, Redux store, MemoryRouter) and the `InMemoryTaskRepository`. Time-dependent
behaviour ("Up next", midnight rollover, overdue) is tested with `vi.useFakeTimers()` and
`vi.setSystemTime()`. Pure modules (`occurrences.ts`, `plannerCommands.ts`, `taskFormSchema`)
get exhaustive unit tests. Capacitor plugins are never imported by components; they are
wrapped in `src/shared/services/native/` and mocked in tests via the module boundary.

**Rationale**: Matches Principle V (behaviour-level tests, colocated) and keeps tests free of
storage and native APIs.

**Alternatives considered**: Upgrading to Vitest 5 / Vite 8 (available, but a toolchain upgrade
is a separate, deliberate change per the constitution and is not needed for this feature).

## R13. Mock-first principle without HTTP endpoints

**Decision**: This feature calls no HTTP API, so there are no MSW handlers to write. The
spirit of Principle IV is kept by the `InMemoryTaskRepository`: `npm run dev:mock`
(`VITE_API_MOCK=true`) selects it with a seeded set of tasks across the current week, and
tests use it by default. The MSW worker, `src/mocks/server.ts` and `handlers.ts` stay in place
(with an empty handler list) so a future sync backend can be mocked without new plumbing.

**Rationale**: Principle IV requires "every endpoint the app calls" to have a handler; with
zero endpoints this is satisfied vacuously, and the deterministic seeded repository gives the
same benefits (no backend needed, exercisable loading/empty/error states).

## R14. Lint gap: TypeScript files are not linted today

**Decision**: Add `typescript-eslint` 8.x and extend the ESLint flat config so the rules apply
to `**/*.{ts,tsx}` (with `parserOptions.project` off for speed), and set
`settings.react.version` to `'detect'`. Add a `lint` run to the merge gate as the constitution
already states.

**Rationale**: The starter's `eslint.config.js` targets only `**/*.{js,jsx}` and installs no
TypeScript parser, so `npm run lint` and the Husky hook silently skip every `.ts/.tsx` file.
Principle II ("ESLint is the single source of style truth") cannot hold until this is fixed.

## R15. Identity and clock

**Decision**: IDs come from `crypto.randomUUID()` (available in Android WebView because the
app is served from the secure `https://localhost` origin). A `useNow()` hook provides the
current time to components, ticking every 30 s and on `visibilitychange`/Capacitor
`appStateChange`, so "Up next" and the midnight rollover (edge case) update without reloads.

**Alternatives considered**: `nanoid` (unnecessary dependency); reading `Date.now()` inline in
components (untestable and never re-renders).

## R16. Design tokens

**Decision**: Define the palette from the reference (warm coral primary `#F26B75`-ish, violet
to coral gradient for "Up next", soft pink page background, white cards, 16–24 px radii) as
CSS custom properties in `src/index.scss`, plus SCSS mixins in
`src/assets/styles/_mixins.scss` for card, focus-ring and reduced-motion helpers. Exact hex
values are finalised during implementation against WCAG AA contrast checks.

**Rationale**: Constitution requires tokens defined once; CSS custom properties allow a later
dark theme without touching components.
