# Research: Task Reminders

**Feature**: `002-task-reminders` | **Date**: 2026-09-22

Versions checked against the npm registry on 2026-09-22.

## R1. Notification delivery: `@capacitor/local-notifications` 8.3.x

**Decision**: Use the official `@capacitor/local-notifications` plugin (8.3.1, peer
`@capacitor/core >= 8`). Reminders are scheduled as local notifications with
`schedule: { at: Date, allowWhileIdle: true }`, a stable integer `id` per occurrence, `extra:
{ taskId, date }` for deep linking, and `channelId: 'reminders'` on Android. The plugin's web
implementation (Notification API + timers) gives the browser fallback for free.

**Rationale**: Reminders must fire with the app closed and after reboots; only the OS can do
that. The official plugin supports scheduling, cancelling, listing pending notifications,
permission checks, Android channels with custom sounds, the exact-alarm setting on Android
12+/14+, and a tap listener. Its web layer means the same code path runs in `npm run dev`.

**Alternatives considered**: Push notifications via a server (needs a backend and accounts,
which the product rules out); a foreground service or WorkManager job (heavy, battery-hostile,
still needs notifications); `capacitor-community` forks (no advantage over the official plugin).

## R2. Exact delivery on Android 12 / 13 / 14+

**Decision**: Declare `SCHEDULE_EXACT_ALARM` in `AndroidManifest.xml`. On the first save of a
task with a reminder, after notification permission, call `checkExactNotificationSetting()`;
if it is not `granted`, show the in-app explanation with a button that calls
`changeExactNotificationSetting()`. Re-check on every app start and resume. When exact alarms
are unavailable, still schedule (the OS delivers inexactly, typically within minutes) and show
the "Reminders may be late" variant of the indicator.

**Rationale**: On Android 12/13 the permission is granted at install; on Android 14+ it is
denied by default for new installs and must be enabled by the user in a system screen. SC-001
(within 60 s) needs exact alarms, but reminders that arrive a few minutes late are better than
none, so the fallback keeps scheduling. `USE_EXACT_ALARM` (auto-granted) is reserved by Play
policy for alarm-clock and calendar apps and was rejected as a policy risk for a todo app.

**Alternatives considered**: `USE_EXACT_ALARM` (policy risk); inexact only (fails SC-001).

## R3. Reconcile, don't track: the scheduling engine is a pure plan + diff

**Decision**: A pure function `computeReminderPlan(doc, now, horizonDays = 14)` derives the
complete set of reminders that *should* exist (one per eligible upcoming occurrence). A
`reconcileReminders(plan, pending)` function diffs it against `getPending()` by id and
content, producing `{ cancel: id[], schedule: ReminderRequest[] }`. `syncReminders()` runs the
diff through a `NotificationGateway` after every successful mutation, on app start, on
resume, after permission changes and when preferences change.

**Rationale**: Every FR-006 case (done, edit, move, delete, series split, end repeat, move to
today, clear time) is covered by one rule: "the OS state must equal the plan". No per-command
bookkeeping, no orphan reminders, idempotent, and trivially unit-testable with a fake
gateway. Re-running on start/resume is also what tops up repeating tasks (FR-008) and restores
everything after a reboot if the OS ever drops alarms.

**Alternatives considered**: Cancel/schedule inside each command (nine code paths, easy to miss
one); storing scheduled ids in the document (drifts from OS state after reboots or setting
changes).

## R4. Stable notification ids

**Decision**: `notificationId(key) = (fnv1a32(key) & 0x7fffffff) || 1` where `key` is the
occurrence key `${taskId}:${date}`. Ids are deterministic, so re-running the plan never
duplicates a reminder, and cancelling by id needs no lookup table.

**Rationale**: Android notification ids are 32-bit signed ints; the plugin requires numbers.
Collisions at 2^31 for a few hundred reminders are negligible; a collision would only merge
two reminders into one and self-heal on the next reconcile.

**Alternatives considered**: Sequential ids stored in the document (state to maintain);
`Math.random()` (not stable across runs).

## R5. Sound: a generated "mellow chime" on a dedicated channel

**Decision**: Ship an original ~1.4 s chime generated by a committed script
(`scripts/generate-chime.py`, standard-library `wave` only): two soft sine tones (C5 523 Hz →
G5 784 Hz) with a faint octave harmonic, gentle attack and exponential decay, 44.1 kHz 16-bit
mono, peak −6 dBFS. Output to `android/app/src/main/res/raw/mellow_chime.wav` and
`public/sounds/mellow_chime.wav`. On Android create channel `reminders` ("Task reminders",
importance HIGH, `sound: 'mellow_chime.wav'`, vibration on, visibility public) once at
startup. On the web, when a reminder fires while the tab is open, play the same file through an
`Audio` element (browsers do not play custom notification sounds).

**Rationale**: FR-016 asks for a distinct soft chime; generating it avoids licensing questions
and binary provenance problems. Android 8+ binds sound to the channel, not the notification,
so a channel with the sound is the only reliable way. Channel sound cannot be changed after
creation; a future sound change must use a new channel id (documented in the contract).

**Alternatives considered**: Downloading a royalty-free sample (provenance/licence review);
device default sound (rejected by FR-016); per-notification `sound` field (ignored on Android
8+).

## R6. Where reminder state lives

**Decision**: Extend the persisted document to version 2: `Task.reminderMinutesBefore`
(`5 | 15 | 30 | 45 | 60 | null`), `OccurrenceOverride.reminderMinutesBefore?`, and a new
`preferences` object `{ remindersEnabled, defaultReminderMinutesBefore, permissionPromptShown }`.
`migrate()` upgrades v1 documents by setting every task's reminder to 15 minutes (FR-015) and
default preferences. Changes go through new `PlannerCommand`s (`setReminderPreferences`) and
the existing create/update commands, so TanStack Query stays the single owner and Redux is
untouched.

**Rationale**: Preferences and reminders are persisted data that every view reads; the
constitution puts that in the Query-owned document. Keeping them in the same document means one
save, one migration path and one repository.

**Alternatives considered**: A separate Preferences key (second repository, two sources of
truth for the plan); a Redux slice with persistence middleware (violates Principle III).

## R7. Deep link from a notification tap

**Decision**: In `AppShell`, register `LocalNotifications.addListener('localNotificationActionPerformed')`
once; on the event, `navigate('/')` and `openTaskDetail({ taskId, date })` from
`notification.extra`. If `findOccurrence` returns null (task since deleted), just show Today.
Capacitor retains the launch event until a listener is attached, so cold starts are handled
by the same code.

**Alternatives considered**: URL-based deep links (needs an intent filter and URL parsing for
no benefit here).

## R8. Permission flow

**Decision**: `requestPermissions()` is called only from the editor's save path, the first time
a task with a reminder is saved (`preferences.permissionPromptShown === false`). The result
is stored; saving proceeds regardless. `checkPermissions()` runs on start/resume to keep the
indicator accurate. The "open system settings" button uses the plugin's
`changeExactNotificationSetting()` for exact alarms and, for notification permission,
Android's app-notification settings intent via `@capacitor/app`'s `openUrl` fallback is not
reliable, so the button opens the app's system settings page through the
`android.settings.APP_NOTIFICATION_SETTINGS` intent implemented in a 20-line native helper
(`NotificationSettingsPlugin`) registered in `MainActivity`.

**Rationale**: FR-009/FR-010 require asking once and never blocking saves; the official plugin
has no "open notification settings" method, and a tiny custom plugin is cleaner than a third
party dependency.

**Alternatives considered**: `capacitor-native-settings` community plugin (adds a dependency
for one intent); asking on app launch (rejected by FR-009).

## R9. Testing

**Decision**: The plan and diff functions get exhaustive unit tests. A `FakeNotificationGateway`
(in-memory pending list, permission state, exact-alarm state, fired events) backs component
and hook tests. `useReminderSync` is tested with fake timers. Notification body formatting is
snapshot-free and asserted literally. Device delivery, reboot restore, exact-alarm behaviour and
the chime are verified manually on an Android device (quickstart), because none of them can
run under jsdom.

## R10. Toolchain impact

**Decision**: No new build tooling. `res/raw` is a plain resource folder; `npx cap sync` copies
the web assets. The manifest gains `SCHEDULE_EXACT_ALARM`; `POST_NOTIFICATIONS` is merged in by
the plugin. Node, Vite, Vitest and ESLint configurations are unchanged.
